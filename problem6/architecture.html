Layered App Architecture

A simple, proven shape for a web or mobile product. Six layers, each with one job. Start small with the left-hand column of every layer, and grow only when real traffic or real requirements push you there.

Example

One request, step by step

What happens when a signed-in user loads their dashboard.

  1. Browser sends GET /api/dashboard with a session cookie or token.
  2. CDN / WAF blocks bad traffic, terminates TLS, forwards to the load balancer.
  3. Gateway verifies the token, checks the rate limit, validates input.
  4. App service checks permissions, then asks the cache for the data.
  5. Cache miss → read from the database, store the result in the cache.
  6. Response returns as JSON; logs, metrics and a trace are recorded.
What can be expanded

Each layer, and how it grows

Every layer has three stages. Most products live happily in Stage 1 for a long time. Move right only when you feel a specific pain.

Client

Renders UI, holds short-lived UI state, calls the API.

Stage 1 · Start
  • Single-page app (React, Vue) or server-rendered pages
  • One API client module
  • Form validation in the browser
Stage 2 · Grow
  • Server-side rendering (Next.js, Nuxt) for SEO and speed
  • Mobile apps sharing the same API
  • Design system and component library
Stage 3 · Scale
  • Backend-for-frontend (BFF) per client type
  • Offline support and local sync
  • Micro-frontends for large teams

Edge

Gets traffic to you fast and keeps bad traffic out.

Stage 1 · Start
  • Managed DNS + free TLS certificate
  • CDN for static files (Cloudflare, CloudFront)
  • One load balancer
Stage 2 · Grow
  • Web Application Firewall rules
  • Bot and DDoS protection
  • Cache API responses at the edge
Stage 3 · Scale
  • Multi-region with geo-routing
  • Edge functions for personalization
  • Automatic failover between regions

API Gateway

One front door that applies the same rules to every request.

Stage 1 · Start
  • Middleware inside the app (auth, CORS, validation)
  • REST with an OpenAPI spec
  • Simple per-IP rate limit
Stage 2 · Grow
  • Dedicated gateway (Kong, AWS API Gateway, Nginx)
  • Per-user and per-key quotas
  • API versioning (/v1, /v2)
Stage 3 · Scale
  • GraphQL or gRPC where it fits
  • Service mesh (Istio, Linkerd) for internal traffic
  • Public developer portal

Application

Where the business rules live. Keep it stateless so you can run many copies.

Stage 1 · Start
  • One well-organized monolith
  • Folders by feature: controller → service → repository
  • Runs in a container
Stage 2 · Grow
  • Modular monolith with strict module boundaries
  • Background jobs for slow work (emails, reports)
  • Horizontal autoscaling
Stage 3 · Scale
  • Split hot modules into microservices
  • Event-driven communication (Kafka, SNS/SQS)
  • Serverless functions for spiky workloads

Data

The source of truth. The hardest layer to change later, so choose carefully.

Stage 1 · Start
  • One managed relational DB (PostgreSQL)
  • Object storage for files (S3)
  • Automated daily backups
Stage 2 · Grow
  • Redis cache for hot reads
  • Read replicas
  • Message queue for async work
  • Search engine for full-text search
Stage 3 · Scale
  • Sharding or partitioning
  • Separate analytics warehouse
  • Specialized stores per need (polyglot)

Observability & DevOps

How you know the system is healthy, and how you ship safely.

Stage 1 · Start
  • Structured JSON logs
  • Uptime check + error tracking (Sentry)
  • CI pipeline: test, build, deploy
Stage 2 · Grow
  • Metrics dashboards and alerts (Prometheus, Grafana, Datadog)
  • Infrastructure as code (Terraform)
  • Staging environment
Stage 3 · Scale
  • Distributed tracing (OpenTelemetry)
  • SLOs and error budgets
  • Blue/green or canary deploys

Hosted providers

Auth0, Clerk, AWS Cognito, Firebase Auth, Supabase Auth. Fastest route to secure login with MFA built in.

Self-hosted

Keycloak, Ory, Authentik. Full control and no per-user fees, but you run and patch it.

Authorization models

RBAC (roles like admin, editor) to start. ABAC or ReBAC (OpenFGA, Cerbos) when permissions depend on ownership or teams.

Simple default

Use an OIDC provider for login, issue short-lived tokens or an HttpOnly session cookie, enforce MFA for admins, and check roles in the application layer on every request.

  • Repository pattern keeps SQL out of business logic
  • Versioned migrations in source control

  • Test a restore, not only the backup
  • Multi-AZ standby for production

  • Indexes and query tuning first
  • Then cache and read replicas
  • Partition or shard last
Security

Defense in depth, layer by layer

No single control is enough. Each layer assumes the one above it might fail. The OWASP Top 10 is a good checklist to review against.

Client

  • Content-Security-Policy header
  • Tokens in HttpOnly, Secure, SameSite cookies, not localStorage
  • Never trust client validation alone
  • Escape output to prevent XSS

Edge

  • TLS 1.2+ everywhere, HSTS on
  • WAF with managed rule sets
  • DDoS and bot protection
  • Only the load balancer is public

API Gateway

  • Validate every input against a schema
  • Rate limit per IP, user and key
  • Strict CORS allow-list
  • Uniform error messages that leak no internals

Application

  • Check permissions on every action (least privilege)
  • Hash passwords with Argon2 or bcrypt
  • Scan dependencies (Dependabot, Snyk)
  • Audit log for sensitive actions

Data

  • Parameterized queries only (no SQL injection)
  • Encrypt at rest and in transit
  • Database in a private subnet
  • Separate DB users with minimal grants

Operations

  • Secrets in a vault (AWS Secrets Manager, Vault)
  • MFA and SSO for all staff accounts
  • Alert on unusual login or error spikes
  • Regular patching and pen tests

Reliability

Plan for parts failing

Networks drop, services slow down, regions go offline. Design so one failure stays small.

Failure-handling patterns

Timeouts + retries always

UseEvery network call. Retry with exponential backoff and jitter.
RiskRetrying non-idempotent calls can double-charge.

Idempotency keys always

UsePayments, orders, any write a client may resend.
RiskNeeds a store of seen keys with expiry.

Circuit breaker

UseCalls to flaky dependencies. Stop calling, fail fast, retry later.
RiskThresholds need tuning.

Graceful degradation

UseNon-core features (recommendations, avatars). Show a fallback.
RiskEvery fallback path needs testing.

Bulkheads

UseSeparate pools or queues so one slow feature can't starve others.
RiskSome idle capacity.

Health checks

UseLiveness and readiness probes so bad instances get replaced.
RiskDeep checks can cascade failures.

Service communication

Call now, or send a message

Use a direct call when the user is waiting for the answer. Use a message when the work can happen a moment later.

Synchronous (request → response)

REST / HTTP default

UsePublic and most internal APIs.
RiskChatty calls add latency.

gRPC

UseFast, typed calls between internal services.
RiskHarder to debug; poor browser support.

GraphQL

UseMany clients needing different shapes of data.
RiskCaching and query cost control.
Asynchronous (fire and continue)

Job queue default

UseBackground work for one consumer. SQS, RabbitMQ, BullMQ.
RiskNeed retries and a dead-letter queue.

Event stream

UseMany consumers, replayable history. Kafka, Kinesis.
RiskHeavy to operate.

Pub/sub

UseFan-out notifications. SNS, Google Pub/Sub, Redis.
RiskOrdering not guaranteed.

Webhooks

UseTelling external systems something happened.
RiskSign payloads; receivers go offline.
Patterns that keep messaging safe

Outbox

Write the event to a table in the same DB transaction, then publish it. The DB and the event never disagree.

Dead-letter queue

Messages that keep failing move aside for inspection instead of blocking the queue.

Idempotent consumers

Delivery is usually at-least-once, so handling the same message twice must be harmless.

Data consistency

When must data be exact right now?

Money and inventory need strong consistency. Feeds, counters and search can be a few seconds behind.

Consistency models

ACID transactions default

UseAnything inside one database.
RiskDoesn't span services.

Eventual consistency

UseRead models, search, caches, analytics.
RiskUsers may briefly see old data.

Optimistic locking

UseConcurrent edits. A version column rejects stale writes.
RiskClients must handle conflicts.

Saga

UseMulti-service workflows with compensating steps (refund, release stock).
RiskComplex; consider a workflow engine (Temporal).
Caching strategies

Cache-aside default

App reads cache, falls back to DB, fills cache. Delete the key on write.

Write-through

Write to cache and DB together. Fresher reads, slower writes.

TTL only

Let entries expire. Simplest, fine when slightly stale data is acceptable.

Zero-downtime schema changes

Use expand → migrate → contract: add the new column, deploy code that writes both, backfill, switch reads, then drop the old column in a later release.

Release strategies

Rolling default

Replace instances a few at a time. Simple; old and new run side by side briefly.

Blue / green

Two full environments; switch traffic at once. Instant rollback, double cost during release.

Canary

Send 1–5% of traffic to the new version, watch metrics, then expand.

Feature flags

Ship code dark, turn on per user or percent. LaunchDarkly, Unleash, GrowthBook.

Environments

Local → dev/preview (per pull request) → staging (production-like data shape) → production. Same container image promoted through each; only config differs.

RiskMigrations run N times.

Privacy basics

  • Collect only what you need
  • Retention rules and auto-deletion
  • Export and delete a user's data on request

Operational

  • Mask PII in logs and traces
  • Audit trail of who accessed what
  • Data residency (EU data stays in EU)

Frameworks

  • GDPR / CCPA: personal data rights
  • SOC 2: B2B security trust
  • PCI DSS: card data (use Stripe to avoid most of it)
  • HIPAA: US health data
Cost

Each stage costs more. Grow on purpose.

Stage 1 · $

Monolith, one DB, PaaS or managed containers. One person can run it.

Stage 2 · $$

Cache, replicas, queues, staging env, monitoring tools. Costs grow with each managed service.

Stage 3 · $$$

Microservices, multi-region, Kubernetes. Needs a platform team; people cost more than servers.

Cost levers

Right-sizing

Match instance size to real usage. Review monthly.

Autoscaling

Scale down at night and on weekends; scale to zero where possible.

Commit discounts

Savings plans or reserved instances for steady baseline load.

Spot instances

Cheap capacity for interruptible jobs and batch work.

Storage tiers

Move old files and logs to cold storage; set log retention.

Tags + budgets

Tag resources by team or feature and alert on budget overruns.

Testing strategy

Many fast tests, few slow ones

The test pyramid: wide base of quick unit tests, narrow top of slow end-to-end tests.

Load testing

k6, Gatling, Locust. Run before launches and big changes.

Decision records

Write down why, not only what

An Architecture Decision Record (ADR) is a short note per big choice, kept in the repo. New teammates learn the reasoning; future you knows when to revisit.

ADR in repo default

Markdown files in docs/adr/, reviewed like code. Templates: MADR, Nygard.

RFC / design doc

Longer proposal for large changes, discussed before building.

Tech radar

Team-wide list of tools to adopt, trial, hold or retire.

# ADR-003: Use PostgreSQL as the primary database
Status:   Accepted · 2026-10-19
Context:  Relational data (users, orders), need transactions, team knows SQL.
Options:  PostgreSQL · MySQL · MongoDB · DynamoDB
Decision: PostgreSQL on a managed service.
Why:      ACID, JSONB for flexible fields, mature tooling, easy hiring.
Trade-off: Must plan for read replicas/partitioning if writes grow a lot.
Revisit:  If a single primary exceeds ~70% CPU at peak.
Rule of thumb: keep it a well-structured monolith on one Postgres database until a measured problem says otherwise. Every layer above can grow independently when it does.
